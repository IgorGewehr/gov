## 3. Dependências / cuidados cross-module

1. **Pass 1 e Pass 2 são as travas de produção** (todos os 5 P0). Pass 2 não depende de Pass 1
   (módulos disjuntos), mas deve esperar o build lane liberar — verify é serial.
2. **ID-1 + ID-2 fecham juntos** (mesma classe: verificação de escopo `CobreEscopo` nos handlers
   administrativos de usuário). Não fechar ID-1 sem ID-2: deixar `EditarUsuario`/`Ativar`/`Desativar`
   abertos reabre vetor adjacente de takeover via troca de e-mail de login.
3. **CF-1 absorve CF-W1** (cadeia ICP-Brasil/revogação) e toca CF-W2 (rotação de KEK) — ao implementar
   o gate de validade no uso, alinhar a validação de cadeia/revogação no mesmo arquivo.
4. **T-D1 (decadência) e T-D2 (prescrição) são o mesmo agregado-família (Tributos)** mas paths distintos
   (lançamento vs cobrança/Dívida Ativa). Ambos no Pass 1; cuidar de não duplicar a checagem de data —
   T-D1 adiciona data do fato gerador ao `Lancamento`; T-D2 usa `EstaPrescrita` já existente.
5. **F-1/F-2/F-3 compartilham `MotorContabil` + `RoteirosCatalogo`** (roteiros já existem como dead code).
   Mesmo módulo (Finanças) → um único agente edit-only para os três, sequencial dentro do módulo, para
   evitar conflito de edição nos handlers/roteiros.
6. **PG-1 consome eventos de RH (`IngestaoRecursosHumanosHandlers`)** mas só lê via Contracts — não há
   acoplamento de edição com RH (RH-D1/RH-W1). PainelGestor isolado no Pass 5; sem conflito com Pass 1.
7. **Transparência TR-L1** (`ValorMonetario.Somar`) é o **mesmo padrão D8** do `ValorMonetario` fiscal
   já refutado em Finanças/Tributos — confirmar qual `ValueObjects/ValorMonetario.cs` é o de Transparência
   (pode haver VO por módulo); não tocar o VO fiscal que já re-arredonda corretamente.
8. **Protocolo P-1 (race do NUP)** exige reserva atômica/sequence — toca Infrastructure + migration.
   Isolar do P-2 (mesmo módulo, mas P-2 é server-side criticidade dependente de TTD não implementada;
   P-2 pode ficar como roadmap se a TTD não entrar no escopo do passe).
9. **Verify é sempre serial** (build lane único). Edição é paralela por módulo disjunto; o gargalo é o
   build+test, não a edição. Não disparar dois verifies concorrentes.
